# Architecture and toolset

## Boundary

`pieceoff-core` owns puzzle definitions, piece topology, joins, versioned room commands/events, and serialization policy. It must not depend on a window, GPU, or media decoder. `pieceoff-server` owns authoritative room state, persistence, membership, and command validation. `pieceoff-app` owns desktop UI, input, rendering, media integration, and optimistic interaction. Add crates only when a real boundary appears.

## Proposed stack

| Need | Candidate | Why / decision gate |
| --- | --- | --- |
| Desktop window and controls | `eframe`/`egui` (implemented) | Cross-platform desktop UI. Validate accessibility and board input as the interface matures. |
| Board rendering | egui textured triangle meshes (implemented) | Core derives deterministic mating-tab contours from media fingerprint and grid position; the desktop client triangulates and renders/picks those polygons. Ctrl-click multi-selection leases linked groups atomically before moving them together. Pieces drawn small use thinned outlines (every 2nd to 16th sample, triangulated on first use, corners always kept), pieces under 7 points wide skip their outline stroke, and drag position updates are sent at most about 30 times a second. A 400-piece table that cost about 16 ms to build and tessellate per frame (770k vertices) now costs about 3 ms (140k), and entering a 400-piece room dropped from about 110 ms to 15 ms; measure with `cargo test --release -p pieceoff-app large_board_frame_cost -- --ignored --nocapture`. A dedicated GPU pipeline is not needed at the 400-piece cap. |
| Video | `MediaDecoderBackend` worker interface (implemented); FFmpeg CLI backend for video/APNG/GIF; native `image` backend for animated WebP | Both backends receive the same playback-control and frame-delivery channels while keeping codec work outside puzzle rules and UI state. Shared seek, loop in/out, and speed; decoder restarts at loop boundaries. FFmpeg is external and optional in bundles; bundles that include it must carry corresponding sources (`docs/FFMPEG.md`). Clip cutting picks whichever video encoder the FFmpeg build has. |
| Media queue | `RoomSnapshot.queue`/`current`/`repeat`/`video_lock` (protocol v8), host-only queue messages, server-side auto-advance | The board (grid, `shape_seed`, piece progress) is fixed when the room is created; the current queue item is only the picture sampled onto it. `media_sha256`/`media_extension`/`media_available` mirror `queue[current]` so older code paths keep working. Switching stores the old item's position and loop range and restores the new item's, keeps the playing state, and never touches pieces. The server checks every 250 ms and advances when the current item passes its loop out (or its known `duration_ms`): `One` is left to the clients' loop, `All` wraps, `Off` pauses at the last item's end. With `Off`/`All` clients hold the last frame instead of wrapping while waiting for that snapshot. A different aspect ratio is centre-cropped to the board with a UV rectangle at render time. Every item uploads once to the content-addressed store, and clients download the current item first, then the following items in play order. A v7 room migrates to a one-item queue repeating that item, with contours unchanged because `shape_seed` starts as the old media-hash seed. |
| Audio | FFmpeg PCM decode played in-process through `cpal` (implemented) | The audio worker feeds the output device so that what is heard follows the room clock: it skips ahead when late, holds when early, and reseeks beyond three seconds. Volume, mute, and a per-device delay are local and apply without restarting. The next loop pass is decoded ahead so loops join without a gap. `cpal` is Apache-2.0 and needs ALSA headers to build on Linux. Sound effects (`sfx.rs`) are synthesised once into PCM and mixed on a second, lazily opened `cpal` stream with their own volume, so they never disturb the clip's audio sync. |
| Multiplayer transport | `axum` WebSockets on `tokio` | Protocol v14 supports imported initial room snapshots, single- and multi-group drag leases, private host upload-token handoff, a host-only puzzle restart, and a tray rearrange any player can request (loose single pieces go back into free tray slots, edges first or shuffled; assembled, placed, and held pieces stay put), live cursors, room chat, board pings, a server-owned solve clock with per-player credits, per-player piece holders, per-room name claims, spectators, an on-request solve timelapse, and a per-room cut style. The server broadcasts authoritative snapshots and ordered events. Older supported room snapshots migrate on load. |
| Room persistence | Atomic JSON snapshots (implemented) | Simple durable rooms on one server; move to a database before hosted multi-node use. |
| Images | `image` | Decode imported still images and thumbnails. Media dimensions are capped at 8192 pixels per side and 40 megapixels total before raster frame decoding. |
| Project/state data | Versioned `.pieceoff` binary envelope with a JSON manifest and embedded media | Rehost puzzle progress on a new room while keeping network identity separate. |
| Diagnostics | `tracing` | Media pipeline and frame timing diagnostics. |
| Build/release | Cargo, rustfmt, Clippy, GitHub Actions compile/test matrix, OS native packaging | Linux launcher and server health smoke test pass. The Windows GNU workspace builds locally; only the core crate has been checked for macOS. Native Windows/macOS launches and installers remain release work. |

The Rust stack is in Cargo.toml and Cargo.lock. FFmpeg is an external executable and is optional in release bundles. Verify exact crate and FFmpeg distribution licenses and native packaging requirements before release. Avoid treating a crate's Rust license as covering bundled codec plugins or example media.

## Video rendering model

One room playback timeline drives one video decoder and, where the source has audio, one audio decoder per client. The `MediaDecoderBackend` interface starts a codec worker with a shared startup contract; FFmpeg and native animated-WebP workers own their decode loops and return frames/errors over channels. Each decoded frame updates one texture shared by the board. Jigsaw-shaped piece meshes sample source UVs from that texture. The server publishes playback state and a timestamp. Each command to a decoder carries the instant its position was read, and both workers pace against that clock rather than counting frames or samples: the video worker shows a frame when it is due, drops frames that are late, and starts the next loop pass early; the audio worker chooses which samples reach the device. Startup and restart delays are therefore caught up instead of carried, and periodic checks only re-read the clock. The prototype supports host play/pause, seek, loop in/out, and speed; audio tempo follows playback speed while volume and mute are local. Both video and native animated-WebP paths retry transient decode failures twice with short delays. If a worker exits, the app restarts it (within a budget of two restarts that refills when a frame arrives) on the next room playback update or, failing that, every two seconds; a watchdog kills an FFmpeg stuck in one read for ten seconds, and a video that decodes to no frames is reported rather than retried. Startup and persistent failures reach the client status, and More → Restart video starts the decoder afresh. Players can locally freeze the current frame as a solving aid while live video and audio continue. If those restarts also fail, More → Restart video, or leaving and rejoining the saved room, resets the retry budget and reloads the selected local media. Pausing the clip does not freeze dragging.

Piece contours are generated from the media fingerprint, the room's cut style, and grid coordinates, so all clients derive identical shared edges without storing a separate shape payload. `RoomSnapshot.cut_style` (protocol v14, default `jigsaw`) picks classic jigsaw pieces, hexagons, or triangles. Every style keeps the `rows × columns` index and puts piece homes at cell corners, so placing, joins, holders and the tray work unchanged; only outlines and neighbours differ (`crates/pieceoff-core/src/tiling.rs`). Hexagons are brick rows offset by half a cell with zig-zag row boundaries (up to six neighbours); triangles alternate up and down with a two-cell base, trapezoids at the side borders (up to three neighbours). Their outlines come from vertices with integer keys and each edge is generated from its lower key, so neighbours trace identical samples; border edges are straight, and knobs shrink when a manual grid stretches cells away from the regular shape. The jigsaw generator is unchanged and pinned by a bit-exact test. Any contour algorithm change that affects rendering should be treated as a compatibility change and covered by an explicit protocol or puzzle-format version decision.

## Multiplayer model

The server assigns a room ID and an 8-character join code (about 40 bits, from an alphabet without look-alike characters; never reused for a live room), accepts guest identity, and persists board snapshots. Clients send intents; the server validates moves, snapping, and joins and broadcasts ordered results. A piece lease prevents two people from moving one piece simultaneously. On disconnect, leases expire; on reconnect, the client receives a fresh snapshot and resumes. Presence and cursors are ephemeral. Persist board and room playback settings, not every cursor movement. A client sends `cursor { x, y }` in board coordinates (at most about 15 a second, only when it moved) and `cursor_hidden` when the pointer leaves the table or the window loses focus. The server drops points that are not finite or off the table and anything over 20 a second per connection or 120 a second per room, without replying, and relays the rest as `cursor { client_id, name, x, y }` to everyone but the sender on a separate cursor channel, so pointer traffic cannot push room events out of a slow client's buffer (a client behind on cursors just skips to newer ones); a player who leaves gets a `cursor_hidden`. Clients forget a cursor after 3 s without an update. `chat { text }` is tidied by the server (line breaks become spaces, control, text-direction, and invisible formatting characters go, trimmed, at most 300 characters; blank lines are dropped), limited to a burst of 5 then 1 a second per connection and 10 a second per room, shared with pings (over that the sender gets an error), stamped with the sender's client ID, name, and server time, and sent to everyone including the sender. Each room keeps its last 100 lines in memory and sends them to a joining player as `chat_history` right after `welcome`, and again to a client that fell behind and was resynced with a snapshot; chat is never written to the snapshot and is gone after a server restart. `ping { x, y }` is checked against the table like a cursor, limited to 3 then 1 a second, and relayed to everyone including the sender; clients show it for 3 s. The server hands out a new client ID on every connection, so clients colour a player's cursor, chat name, and pings from a hash of the display name, which survives a reconnect. `RoomSnapshot.stats` (v11) is the room's solve clock and credits, kept by core `RoomRuntime::apply`: the clock starts at the first piece picked up after the room is made or restarted, stops when the puzzle completes, and runs only while someone is connected (hosts call `set_occupied`; the axum server does on every join and leave). It is stored as banked `elapsed_ms` plus `running_since_ms` on the server clock, so clients tick it locally from the last update with no per-second messages, against the server clock learned from `welcome.server_now_ms` (chat ages and the shared playback position use the same offset), so a client with a wrong clock still shows the right time. A saved snapshot banks and stops it (`for_storage`), so server downtime never counts. Each drop credits the pieces it brought into the picture (snapped, or joined to a neighbour; a group snapping whole adds nothing new) to the dropper's display name, at most 32 names; the credits always add up to the piece count. `pieces_changed` carries `stats` only when they changed. A restart clears both; `.pieceoff` packages keep them, stopped, and imported stats are tidied. `RoomSnapshot.holders` (v12) are players' sorting areas, checked in core (`holders.rs`): `create_holder`/`update_holder`/`delete_holder` messages, owner by display name, at most 4 per player and 16 per room, 2–12 cells a side, on the table but clear of the board, the tray (each padded by 0.3 cell), and other holders. A loose piece is inside a holder when the centre of its cell is (top and left edges inclusive); a group with any member inside someone else's holder cannot be acquired by anyone but the owner, so `drag_start` and `drag_start_selection` are refused with "That piece is in <owner>'s holder". Dropping into a holder is allowed. Moving a holder carries the loose, unheld groups inside by the same (table-clamped) offset, except a group another player's holder also reserves and a group that would land in another player's holder; resizing moves nothing. `rearrange_tray` skips pieces in holders and tray slots under one. Holder changes ride on `pieces_changed` as `holders` (the full list, only when it changed), like `stats`. The server's 250 ms ticker calls `tick_holders`, which stamps `owner_away_since_ms` when an owner has no connection and removes the holder 10 minutes later (pieces stay put); the stamp, its clearing when the name returns, and the removal are each announced the same way and saved. Because holders, credits, and colours key by display name, names are claimed per room (core `claims.rs`): each client makes a private random 128-bit `player_key` once, keeps it in its settings, and sends it in `create_room`/`join_room` (an optional field, so v12 stands). The first keyed player under a name (compared without case) claims it; the server keeps a SHA-256 of the key salted with the room ID, never the key, and refuses the name to any other key or to a keyless (older) client with "That name is taken in this room", plus how to get it back. A keyless client may use a name nobody claimed and nobody in the room is using, and claims nothing. The same key rejoining replaces its earlier connection, which gets an error saying the name was opened in another window or device with the same settings (clients do not reconnect after it) and is closed without a `peer_left`. A claim lapses like a holder: the ticker's `tick_claims` stamps `away_since_ms` when nobody is in the room under the name, clears it when someone is, and drops the claim 10 minutes after the stamp, expiring that name's holders in the same tick so nobody inherits them; then any key or keyless client may take the name. The host may free an absent player's name sooner with `release_name { name }` (refused for a name in use and for anyone but the host), which drops the claim and that name's holders at once and is announced as a `pieces_changed`. So a player who moved to another computer or lost their settings gets their name back. Spectators (v13) join with `join_room { spectator: true }` and are kept in `RoomRuntime.spectators`, apart from `names`, so they never count toward the 8-player limit, the solve clock (a room with only spectators is paused, and spectators present are sent a snapshot when the clock pauses or resumes), holder presence, credits, or hosting, and never get an upload token; at most 16 per room. They claim no name but may not watch under one another player's key has claimed. They receive everything players do; `apply` refuses every message from them. Chat is allowed; pings are refused with an error and their cursors are dropped, so players never see them. `welcome` carries `spectator` and `spectators`, and `peer_joined`/`peer_left` carry `spectator`. `RoomRuntime.timelapse` (core `timelapse.rs`) records the current solve: every piece's position (rounded to whole pixels, `[id, x, y]`) just before the first pickup or rearrange, then a frame per settling change (`drag_end`, `drag_end_selection`, `rearrange_tray`, `update_holder`) with the moved pieces and the solve-clock time. Past 20,000 positions, neighbouring frames merge pairwise (later positions win, `condensed` is set), so the replay still ends on the room's layout. A restart clears it. It is not in `RoomSnapshot`; the server saves the room as core `StoredRoom` (the snapshot flattened plus `name_claims` and `timelapse`, compact JSON; older files load with none) and answers `request_timelapse` to the asker alone with `timelapse { timelapse }`, two in a row then one every 10 s per connection. `.pieceoff` export leaves it out (it is server-side and can be large). Clients replay it locally by step, animating each step's pieces and working out placement and joins from positions. Start with private invite rooms; public catalog and accounts are later. Keep the wire schema versioned for future web/mobile clients. Clients open `/ws?protocol=<PROTOCOL_VERSION>`; a server on another version answers with one `error` telling the player to update and closes, instead of messages the app cannot parse (a client that sends no version is let through, as older apps do).

For video rooms, the host uploads one content-addressed media asset to the room server. Uploads stream to a temporary file, must match the room SHA-256, and are installed atomically. The server caps each asset at `PIECEOFF_MAX_MEDIA_BYTES` (16 GiB by default; a larger declared length is refused before reading) and reserves each upload's space against a configurable 50 GiB aggregate media quota, so uploads of different rooms run at the same time. Downloads honour HTTP `Range`; the client keeps one `.part` file per hash and resumes it, retrying with backoff. Transfers have connect and idle timeouts but no total limit, and the status line shows bytes moved; invited clients may download it or skip transfer when their local SHA-256 matches. Media is stored under `PIECEOFF_DATA_DIR/media/` and room snapshots record its availability. Disconnected rooms expire after 90 days by default (`PIECEOFF_ROOM_TTL_DAYS=0` disables expiry); active rooms remain, and assets are removed only after their last room expires. The server can sit behind an HTTPS reverse proxy: clients accept `wss://` room URLs and use the matching HTTPS endpoint for media transfers. Direct server TLS remains future work. For an internet-facing server the process enforces its own limits (rooms, sockets, message size, per-address connection and failed-join rates, browser origins), reads its settings strictly from `PIECEOFF_*` variables, and saves all rooms on SIGTERM; see `docs/DEPLOYMENT.md`.

## Package model

The `.pieceoff` package starts with the eight-byte `PCOFFPKG` signature, a little-endian manifest length, and a little-endian media length, followed by a JSON manifest and the source media bytes. The manifest carries the versioned room snapshot; the media is capped at the client ceiling of 64 GiB and verified against the snapshot SHA-256 when opening. The reader writes to a content-addressed cache and never extracts archive paths. Export clears invite codes, room IDs, host IDs, drag leases, and active playback while preserving piece positions, linked groups, completion state, and the playhead. Opening a package creates a new room identity and uploads the embedded asset. Autosave remains server-owned; larger media can be supported later through an external-media/relink mode.

## Controls

Shortcuts are `Action`s (`controls.rs`) bound to `Binding`s (a key plus Ctrl/Shift/Alt). Only bindings that differ from the built-in defaults are saved in `settings.json` (`keybindings`, keyed by stable action ids), so defaults added later reach players who never customised that action; an action saved with an empty list is deliberately unbound, and a list with nothing readable falls back to the defaults. Two bindings conflict when one would also fire for the other's keypress (same key, nested modifiers); the Controls window refuses a clashing key and names the action that owns it. Escape is fixed. Mouse options live in `settings.mouse` and are clamped on load. Tray tidy and shuffle ship unbound because they change every player's view.

## Puzzle library

The client keeps a shelf under its data directory (`library/`): an atomically written `index.json` plus one `<id>.pieceoff` package and one `<id>.png` thumbnail per entry. Packages are the unit of storage, so a library entry is the same portable file as **Save package…** produces and can be exported or imported unchanged. An entry records title, grid, progress (settled pieces as a percentage, computed by `RoomSnapshot::progress_percent`), and times. Index entries whose package has gone missing are dropped on load; an unreadable index yields an empty shelf and a notice rather than blocking the app. Saving, importing, and thumbnailing run on worker threads because they hash and copy media of many gigabytes. A room started with **Resume** is linked to its entry and writes progress back when the player leaves; **New game** reuses the media with a fresh cut and does not touch the saved progress.

## Compatibility

Any future legacy-format reader should be an isolated importer with original parsing code, documented observable behavior, and a review of the format and fixture rights. Keep the native package independent of legacy data models.
